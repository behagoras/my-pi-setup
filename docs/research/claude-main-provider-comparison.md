# Claude as Pi's main subscription-backed provider

**Checked:** 2026-07-26. **Target:** this repository's `@earendil-works/pi-*` 0.82.x stack. Scores are out of 100 and weight main-chat correctness/tool bridging (30), session behavior (15), 0.82 compatibility (15), authentication/policy risk (15), maintenance/tests (15), and install/security ergonomics (10).

## Recommendation

**Install an exact-pinned `@vanillagreen/pi-claude-bridge` release first; do not reimplement it.** It is the only candidate that combines current 0.82.x parity, native `@earendil-works` peer dependencies, active Pi-tool execution (including dynamically discovered custom tools), robust Claude-session recovery, an npm update path, and a substantial current test suite. Start with an exact npm pin rather than `latest`; review each upgrade because the package and its bundled Agent SDK/runtime are changing quickly:

```sh
pi install npm:@vanillagreen/pi-claude-bridge@1.9.0
```

If reproducible/offline deployment is required, **vendor that exact npm artifact plus its license and integrity metadata**, not a moving monorepo checkout. Keep optional Claude connectors off (they bypass Pi's executor/consent lifecycle), and do not enable the bridge until the user has authenticated the official `claude` CLI and run a smoke test with this repo's `rg`, `fd`, workflow, and subagent tools. Do not vendor or reimplement `pi-o-my` as the default: it is a useful reference implementation but currently fails a 0.82 typecheck and includes repo-specific compaction policy. Do not install the published `pi-claude-cli` 0.3.1 here: it targets the old `@mariozechner/*` 0.52 API and has a current 0.80 compatibility/empty-response report.

## Findings

### 1. `@vanillagreen/pi-claude-bridge`

This is a Pi custom provider, not a delegation tool: Claude handles the ordinary assistant stream while Pi owns the TUI, tool registry, execution, hooks, and JSONL session. Its package documentation describes result-gated tool turns and continuity over compaction, tree navigation, and abort recovery; the source registers `streamSimple`, builds an in-process MCP surface from active Pi tools, correlates Pi tool results back to the SDK query, and records/resumes Claude session IDs ([package metadata/README](https://www.npmjs.com/package/@vanillagreen/pi-claude-bridge), [pinned provider source](https://github.com/vanillagreencom/vstack/blob/a634e17521f8d4354c8bdfe1ad1b5f45a5380ed0/pi-extensions/pi-claude-bridge/src/index.ts)).

It is the best fit for custom workflow tools because it snapshots Pi's registry instead of assuming only stock names. Settings can isolate filesystem MCP configuration and suppress Claude cloud MCPs, reducing duplicate-tool/confused-authority risk. Optional account connectors are different: they execute on Claude's side rather than through Pi and should remain disabled. The tradeoff is complexity: it bundles an Agent SDK/runtime, session I/O and translation code, and its curated aliases can lead Pi's own catalog. Recent commits explicitly aligned runtime behavior with Pi 0.82.1 and wired package tests into CI, but rapid churn makes exact pins important ([current package history](https://github.com/vanillagreencom/vstack/commits/main/pi-extensions/pi-claude-bridge), [npm versions](https://www.npmjs.com/package/@vanillagreen/pi-claude-bridge?activeTab=versions)).

### 2. `pi-o-my/custom-provider-claude-agent-sdk`

This is the cleanest architectural specimen: it holds one SDK query open per Pi branch and uses MCP only as the proposal/result bridge; Pi remains the actual tool executor and recorder ([extension source](https://github.com/joshuadavidthomas/pi-o-my/tree/main/extensions/custom-provider-claude-agent-sdk), [repository README](https://github.com/joshuadavidthomas/pi-o-my)). It imports the same `@earendil-works` family used here, and recent commits fixed 1M-window selection and sibling parallel-tool envelopes ([path history](https://github.com/joshuadavidthomas/pi-o-my/commits/main/extensions/custom-provider-claude-agent-sdk)).

It loses on compatibility and productization. A clean typecheck against `@earendil-works/pi-*` 0.82.0 fails because the extension calls the removed `getModels` export, so matching package scope is not enough. It is a workspace inside a personal setup rather than a separately versioned provider package, so installation means porting/vendoring code and owning future merges. More importantly, its July 2026 compaction hook deliberately sends SDK-model compaction through `gpt-5.5`; that is a surprising cross-provider dependency and conflicts with a simple “Claude subscription is the main provider” operational model. Reuse its live-query ideas, not the whole extension, unless the catalog API and that policy are consciously redesigned and tested.

### 3. `rchern/pi-claude-cli`

This wraps the official CLI rather than calling the Agent SDK directly. Each request launches `claude -p` in stream-json mode and later uses `--resume`; a schema-only MCP server tells Claude about Pi tools while a break-early protocol returns calls for Pi execution ([README/source repository](https://github.com/rchern/pi-claude-cli), [official CLI flags](https://docs.anthropic.com/en/docs/claude-code/cli-reference)).

The design has a smaller direct dependency graph, but it is the weakest current fit. npm 0.3.1 declares peers on `@mariozechner/pi-ai` and `@mariozechner/pi-coding-agent` 0.52, not this fork. Open issue #30 reports empty responses on current Pi and proposes a compatibility fork; other open issues cover MCP initialization, context-limit propagation, and tool visibility ([issues](https://github.com/rchern/pi-claude-cli/issues)). Its hard-coded `Glob → find` mapping already produced a “Tool find not found” loop, demonstrating exactly the drift risk posed by this repo's `fd`/`rg` and workflow tools ([issue #13](https://github.com/rchern/pi-claude-cli/issues/13)). Its subprocess also omits `--strict-mcp-config` and a constrained `--tools` set, so inherited Claude MCP/internal tools can run outside Pi's usual tool lifecycle; temporary MCP/config files are not cleaned up, and its predictable PID-based system-prompt temp path deserves hardening ([provider](https://github.com/rchern/pi-claude-cli/blob/e0c9a12ac21be4c197e82795f7207746f3183028/src/provider.ts), [MCP config](https://github.com/rchern/pi-claude-cli/blob/e0c9a12ac21be4c197e82795f7207746f3183028/src/mcp-config.ts)).

## Compatibility and conflict audit

Installed 0.82.0 exposes the necessary extension seam: `pi.registerProvider(name, { api, models, streamSimple })`, immediate model-runtime registration, and a session-owned tool registry. Pi's official documentation treats custom `streamSimple` implementations as the supported route for nonstandard APIs ([Pi custom-provider docs](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/custom-provider.md), [0.82 model runtime](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/model-runtime.ts)). Therefore the principal compatibility question is package identity: the first two use `@earendil-works/*`; released `pi-claude-cli` uses the pre-fork `@mariozechner/*` types.

Pi's JSONL session remains authoritative in every design, but Claude has a second session state. Switching providers, branching/tree navigation, compaction, or deleting Claude's local session can desynchronize the two histories. The vanillagreen bridge has the most explicit recovery logic; `pi-o-my` has the most elegant live-session behavior; CLI resume is most exposed to missing/stale CLI session IDs. None offers true live model discovery: all publish or mirror aliases, so unknown/new model IDs should be treated as a release/configuration task.

All three are full-trust extensions: they can see prompts, tool schemas/results, cwd, and child-process environment. Keep credentials inside the official Claude CLI/SDK path; never copy OAuth tokens into Pi config. Avoid simultaneously loading more than one candidate because provider aliases, duplicated MCP surfaces, process cleanup, and prompt forwarding can conflict.

## Authentication and policy caveat

Anthropic officially supports logging the **Claude Code CLI** into Claude Pro/Max and says that usage shares the plan's limits; the CLI securely stores its own credentials and auto-updates ([Claude Code setup](https://docs.anthropic.com/en/docs/claude-code/setup), [Pro/Max usage](https://support.anthropic.com/en/articles/11145838-using-claude-code-with-your-pro-or-max-plan)). The CLI officially supports `-p`, stream-json, and session resume, so subprocess use relies on documented CLI surfaces ([CLI reference](https://docs.anthropic.com/en/docs/claude-code/cli-reference)).

That does **not** make a Claude subscription a general API entitlement: Anthropic states that Claude.ai plans and Console API billing are separate ([billing policy](https://support.anthropic.com/en/articles/9876003-i-subscribe-to-a-paid-claude-ai-plan-why-do-i-have-to-pay-separately-for-api-usage-on-console)). Anthropic's current June 2026 guidance explicitly says that Agent SDK, `claude -p`, and third-party applications may **for now** draw from subscription limits, with advance notice before that changes; separate login guidance still prohibits misrepresenting identity or improperly routing traffic around limits ([Claude-plan Agent SDK guidance](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan), [login/usage policy](https://support.claude.com/en/articles/13189465-log-in-to-your-claude-account)). Agent SDK licensing remains governed by Anthropic's Commercial Terms ([official Agent SDK repository](https://github.com/anthropics/claude-agent-sdk-typescript)). Thus local single-user use through the already-authenticated official runtime is currently documented, but it is policy/commercially unstable—not a right to extract tokens, redistribute access, or serve other users. Recheck the current terms before upgrades or any deployment beyond this machine.
